# API 通知系统

内部通知投递服务：接收业务系统提交的外部 HTTP 通知请求，尽可能可靠地投递到目标供应商。

一句话概括它的价值：**业务系统只管把通知交出来，剩下的重试、退避、隔离、死信、排障全部由这个服务负责。**

| | |
|---|---|
| 语言 / 运行时 | Go 1.22，无 CGO |
| 外部依赖 | 无。持久化用嵌入式 SQLite（纯 Go 驱动），不需要 Docker / Redis / MQ |
| 投递语义 | 至少一次（at-least-once） |
| 代码量 | 约 3800 行实现 + 3200 行测试，111 个测试用例，`internal/` 语句覆盖率 88.1% |

## 快速开始

只需要 Go 1.22+，不需要任何外部中间件。

```bash
# 一键演示：正常投递 → 幂等 → 故障重试 → 死信 → 人工重投 → 熔断 → 故障隔离
make demo

# 或者分开跑
make test          # 全部测试
make test-race     # 带竞态检测
make validate      # 只校验配置
make build         # 产物在 bin/
```

`make demo` 会自动起 3 个模拟供应商和一个 notifyd，然后依次演示 7 个场景，
包括把下游切成 503 再恢复、观察熔断器状态变化、死信重投等。全程约 15 秒。

提交一条通知：

```bash
curl -X POST localhost:8080/v1/notifications \
  -H 'Content-Type: application/json' \
  -d '{
        "endpoint": "crm",
        "idempotency_key": "order-1001-paid",
        "payload": {"contact_id": "c-1001", "status": "active"}
      }'
# → 202 {"id":"01M2Z...","status":"pending","endpoint":"crm","duplicate":false,...}
```

## 一、我对问题的理解

需求描述里有三句话定义了这个系统的全部性质，我认为抓住它们比功能齐全更重要：

> - 业务系统**不需要关心外部 API 的返回值**
> - 只需确保通知请求能够**被稳定、可靠地送达**
> - 不同供应商的**请求地址、Header、Body 格式都不同**

我从这三句话里读出的真实问题是：

**1. 这不是一个"发 HTTP 请求"的问题，而是一个"把易失的外部依赖从业务主链路上摘下来"的问题。**

如果业务系统直接调供应商 API，那么供应商的延迟会变成业务接口的延迟，供应商的宕机会变成业务的失败率，
而"用户注册成功了但广告系统没收到"这种不一致会散落在每个业务系统里各自处理。
本系统的价值不在于它会发 HTTP，而在于它把「通知一定会被送到」这件事变成了一个可以被独立运维、
独立扩容、独立观测的承诺。所以入口必须**先持久化再返回**，而且绝不能同步等待投递结果。

**2. "不关心返回值"不等于"不关心结果"。**

业务系统不关心 CRM 返回的 JSON 内容，但一定有人关心「这条通知到底有没有送到」。
这个人是出问题时来查的运维和研发。所以我必须区分"业务语义上的返回值"（不解析、不理解、只截断存一段）
和"投递结果本身"（必须完整记录每一次尝试、状态码、耗时、错误），并且提供一个能一次说清楚现状的查询接口。

**3. "格式不同"是配置问题，不是架构问题。**

三个供应商三种 Header、三种 Body，很容易被设计成一个插件体系或转换 DSL。
但仔细想，差异全部可以被「一份 endpoint 配置」吸收：URL、Header、超时、重试策略、成功码判定。
真正需要写代码的只有 Body 结构映射，而这恰恰是业务语义最重的部分——我选择把它留在业务系统（详见系统边界）。

**4. 最需要被明确定义的其实是"失败"。**

"可靠送达"听起来是个投递问题，实际上是个分类问题：对方返回 503 和返回 400，
在"没送成功"这一点上完全一样，但正确的处理方式截然相反。前者应该退避重试，后者应该立刻停手叫人。
把这两者混在一起（无脑重试所有失败），系统会表现出两个很难受的症状：
真故障时把下游打得更死，真错误时把人工介入推迟几小时。所以本系统里花最多心思的地方是**失败分类**，
而不是重试机制本身。

## 二、整体架构与核心设计

### 2.1 数据流

```
                 ┌──────────────────────── notifyd 单进程 ────────────────────────┐
业务系统          │                                                                │
  │  POST         │   ┌──────────┐   写入并落盘    ┌───────────────────────────┐  │
  ├──────────────►│──►│ 入口 API │ ──────────────► │  SQLite 持久化队列         │  │
  │  202 Accepted │   │ (幂等)   │ ◄────────────── │  notifications (状态机)    │  │
  │◄──────────────│───┘          │   返回任务 ID   │  delivery_attempts (审计)  │  │
                 │   └────┬─────┘                 └─────────┬─────────────────┘  │
                 │        │ Wake()                          │ 按 endpoint 领取     │
                 │        ▼                                 │ + lease              │
                 │   ┌─────────────────────────────────────▼──────────────────┐  │
                 │   │  调度器（单 goroutine 循环）                             │  │
                 │   │   额度 = min(该 endpoint 空闲并发, 熔断允许量, 批大小)    │  │
                 │   └────┬──────────────┬──────────────┬────────────────────┘  │
                 │        │              │              │                        │
                 │   ┌────▼────┐   ┌────▼────┐   ┌────▼────┐   每 endpoint 独立   │
                 │   │ worker  │   │ worker  │   │ worker  │   并发池 + 熔断器     │
                 │   └────┬────┘   └────┬────┘   └────┬────┘                      │
                 │        │             │             │                            │
                 │   ┌────▼─────────────▼─────────────▼────┐                      │
                 │   │ lease 回收器（崩溃恢复）              │                      │
                 │   └──────────────────────────────────────┘                      │
                 └────────┬──────────────┬──────────────┬─────────────────────────┘
                          ▼              ▼              ▼
                     广告系统          CRM            库存系统
```

### 2.2 状态机

整个系统的正确性建立在一个只有 5 个状态的状态机上。它被显式编码成一张表（`internal/model`），
存储层每次状态写入都要先过这张表，避免"succeeded 又被改回 pending"这类脏迁移散落在各处的 if 判断里。

```
                 ┌──────────────── 退避后重试 ─────────────────┐
                 ▼                                             │
 [pending] ──领取──► [in_flight] ──2xx──────────────► [succeeded]
     ▲                    │                                    │
     │                    ├── 可重试失败 / lease 过期 ──────────┘
     │                    │
     │                    └── 不可重试失败 / 预算耗尽 ──► [dead]
     │                                                     │
     └──────────────── 人工重投（admin API）────────────────┘

 [pending] ──人工取消──► [canceled]
```

`succeeded` / `canceled` 是终态；`dead` 是「可人工干预的终态」。

### 2.3 三个核心机制

**① 持久化队列 + lease（可见性超时）**

没有引入消息队列，队列就是数据库里的一张表。领取任务不是删除记录，而是打上一个带过期时间的租约：

```sql
-- 领取（在一个事务里）
SELECT ... FROM notifications
 WHERE status='pending' AND endpoint=? AND next_attempt_at<=?
 ORDER BY next_attempt_at LIMIT ?;
UPDATE notifications SET status='in_flight', lease_owner=?, lease_expires_at=?
 WHERE status='pending' AND id IN (...);
```

所有写回都带上 `AND status='in_flight' AND lease_owner=?` 做乐观校验。
这一个条件同时解决了三个问题：进程崩溃后任务能被回收重放（lease 过期）、
被回收的任务不会被原持有者事后覆盖（owner 不匹配则写回失败）、
多实例可以安全地共享同一张表（互相看不到对方的 lease）。

**② 按 endpoint 分别领取 + 每 endpoint 独立并发池**

这是我认为本设计里最关键的一个选择。常见做法是「一个全局 worker 池从全局队列取任务」，
但那样一个卡死的供应商会把池子占满，拖垮所有其他供应商的通知——即队头阻塞。

本系统的调度循环遍历每个 endpoint，各自计算额度、各自领取、各自有独立的并发信号量。
一个供应商挂掉，最多只能占满属于它自己的那几个槽位。
`TestSlowVendorDoesNotBlockOtherEndpoints` 就是这个设计的验收标准：
让一个 endpoint 的请求全部拖到超时并持续堆积，同时验证健康 endpoint 的通知仍在几十毫秒内送达。

**③ 熔断期间不消耗重试预算**

熔断器打开时，任务**根本不会被从队列里领取出来**，因此 `attempt` 不增加。

这和常见实现不同。常见做法是照常取出任务、直接判失败、`attempt+1`。
那样的话下游宕机 10 分钟就能把所有在途通知的重试预算全部烧完、全部推进死信——
而这些通知本来只需要等下游恢复就能成功。熔断的意义是"先别发，等一等"，
而不是"快速把失败次数用完"。

## 三、系统边界

### 3.1 我选择在这个系统里解决的问题

| 问题 | 解决方式 |
|---|---|
| 通知不能丢 | 入口先落盘再返回 202；SQLite `synchronous=FULL`，断电也不丢已提交事务 |
| 业务系统不能被外部延迟传染 | 入口永不同步投递，只写队列；投递全在后台 |
| 外部系统临时故障 | 指数退避 + 抖动自动重试，可配预算上限 |
| 外部系统长期不可用 | 熔断（不烧预算）+ 预算耗尽后进死信 + 人工重投接口 |
| 重复提交 | 入口按 `(endpoint, idempotency_key)` 幂等去重 |
| 下游收到重复通知 | 注入稳定的 `X-Notification-Id` / `X-Notification-Attempt`，让下游能去重 |
| 一个供应商拖垮全部 | 按 endpoint 分别领取 + 独立并发上限 + 独立熔断器 |
| 供应商格式差异 | endpoint 配置（URL / Header / 成功码 / 超时 / 重试策略）+ 可选 body 模板 |
| 凭据管理 | 集中在服务配置，`${env:VAR}` 注入，任何读接口都不回显值 |
| 进程崩溃 / 发布重启 | lease 过期回收 + 优雅关闭（在途投递跑完或重新排期） |
| 出问题时能查 | 每次尝试的状态码/耗时/错误/响应片段全部留档，一个接口查全 |
| 能否被监控 | Prometheus 指标：队列深度、投递结果、耗时分布、熔断状态、lease 回收数 |
| 误用防护 | body 大小、header 数量/长度、CRLF 注入、重试预算上限、指标标签基数 |

### 3.2 我明确选择不解决的问题

这一节比上一节更重要。**不解决**不等于遗漏，每一条都有我不做它的理由。

**① 不做 exactly-once（恰好一次）**

做不到，而且假装做得到会更危险。只要"发出 HTTP 请求"和"记录已发送"是两个独立动作，
进程就可能在两者之间崩溃，重启后无法区分"没发出去"和"发出去了但没记上"。
真正的 exactly-once 需要下游配合做分布式事务或幂等接收，这不是通知服务能单方面承诺的。

我的做法是：诚实地提供 at-least-once，并**主动为下游去重创造条件**
（注入稳定 ID 和尝试序号）。这样系统整体行为可以收敛到"业务上只生效一次"，
但那最后一步的责任明确在下游，而不是被我含糊地承诺掉。

**② 不保证投递顺序**

没有实现「同一实体的通知按提交顺序投递」。原因是顺序保证的代价极高：
需要按 key 分区串行化，一条卡住就要阻塞整个分区，直接和"故障隔离"冲突。
而需求里的三个例子（注册回传、改 Contact 状态、库存变更）都是独立事件，
本身不依赖顺序。如果将来真有场景需要顺序，我倾向于让业务方在 payload 里带版本号/时间戳，
由下游做 last-write-wins，而不是在通知服务里引入分区串行化。

**③ 不解析、不理解外部 API 的返回值**

需求明确说了业务系统不关心返回值。我只看 HTTP 状态码来判定投递结果，
响应体只截断保留 1KB 给人排障用。绝不去解析 `{"code": -1}` 这种藏在 200 里的业务错误——
一旦开始做，通知服务就要跟着每个供应商的错误码体系迭代，变成一个永远在改的胶水单点。
需要这种判定时，用 `success_status_codes` 配置能覆盖大部分情况，覆盖不了的属于业务集成问题。

**④ 不做通用的 payload 转换引擎**

我只提供了一个极简的 Go `text/template` 作为"逃生舱"（`body_template`），
刻意没有引入 JSONata / Jolt / 自研 DSL。
Body 结构映射是业务语义，主战场应该在业务系统里。把它放进通知服务意味着：
每次供应商改字段都要改通知服务的配置并发布，通知服务的发布风险覆盖所有业务方，
而且调试一个 DSL 表达式比调试一段业务代码难得多。
这是一条我认为很容易被"做得更通用"诱惑而走错的边界。

**⑤ 不做调用方身份认证与授权**

业务提交入口没有做鉴权。这不是偷懒，而是认为它属于基础设施层：
内网服务间认证应该由服务网格（mTLS）或统一网关（JWT）解决，
在每个内部服务里各自实现一套身份体系是重复劳动，而且更容易做错。
管理接口（重投/取消/列表）是例外——它有破坏性且可能被人从浏览器误触，
所以加了一个简单的 token，并且在未配置 token 时每次访问都打告警日志，
防止"本地开发省事"的配置被无声地带到生产。

**⑥ 不做分布式限流 / 全局 QPS 配额**

只做了单实例的 per-endpoint 并发上限。真正的全局 QPS 配额需要共享计数器（Redis）
或配额中心，会给本来无外部依赖的服务引入一个新的可用性依赖。
并发上限已经能防止打爆下游（并发 × 1/延迟 就是实际 QPS 上界），
真需要精确 QPS 时再引入，那时应该和限流基础设施统一，而不是自己造一个。

**⑦ 不做通知内容的业务校验**

不校验 payload 里有没有 `contact_id`、库存变更数量是否合法。
通知服务不理解业务语义，这类校验放在这里只会产生虚假的安全感（漏校验）
和虚假的耦合（改业务规则要改通知服务）。只做结构性校验：是不是合法 JSON、有没有超大、有没有注入。

**⑧ 不做 fan-out / 订阅路由**

一条通知对应一个明确的 endpoint，不支持"一个事件广播给 N 个订阅者"。
那是事件总线的职责，和"可靠投递到指定地址"是两个不同的产品。
业务方需要通知两个系统时，提交两条通知即可——这样两个供应商的失败也能被独立重试和隔离，
反而比 fan-out 更符合本系统的隔离原则。

**⑨ 不做数据归档 / 冷热分离**

`notifications` 表会一直增长。第一版不做归档，因为在没有真实流量数据之前，
归档策略（保留多久、归档到哪、succeeded 是否立即可删）全是猜测。
我选择先把「队列深度」和「各状态计数」做成指标暴露出来，
等看到真实增长曲线再决定策略。这是我认为更诚实的处理方式——
预先实现一个猜出来的归档策略，大概率要重写。

## 四、可靠性与失败处理

### 4.1 投递语义：至少一次（at-least-once）

**为什么是 at-least-once：**

- **下界（不丢）**：入口在返回 202 之前，通知已经落盘（`synchronous=FULL`）。
  之后无论进程崩溃、机器重启、下游宕机多久，任务都还在表里。
  落库失败时返回 503 而**绝不返回 202**——返回 202 就等于承诺了一条我们其实没接住的通知，
  业务方会据此认为通知已在路上，这比直接失败危险得多。
- **上界（可能重复）**：重复来自两个不可消除的窗口。
  一是 HTTP 请求已到达下游、但我们在记录结果前崩溃了；
  二是投递耗时超过 lease、任务被回收后由另一个 worker 重放。

**对重复的三层处理：**

1. **入口去重**：`(endpoint, idempotency_key)` 唯一索引。业务系统因超时重发 5 次，
   只会产生 1 条通知、返回同一个 ID（重复提交返回 200 + `duplicate: true`，首次是 202，
   让调用方能区分这两种情况）。
2. **为下游去重创造条件**：每次请求都注入 `X-Notification-Id`（同一通知跨所有重试保持不变）、
   `X-Notification-Attempt`、`X-Idempotency-Key`。下游只要记住 ID 就能去重。
3. **让重复可观测**：`mockvendor` 会明确标记出「同一个 ID 被成功接收了不止一次」，
   让 at-least-once 的代价变成可以被看到的事实，而不是一句口头承诺。

**为什么不是 at-most-once**：需求要求"可靠送达"，而 at-most-once 意味着不确定时宁可不发。
对于"付款成功要改 CRM 状态"这类场景，漏发的代价（状态永久不一致，需要人工对账）
远大于重发的代价（下游看到一次重复请求）。

### 4.2 失败分类：本系统最核心的判断

| 情况 | 判定 | 处理 | 是否计入熔断 |
|---|---|---|---|
| 2xx（或配置的 `success_status_codes`） | 成功 | 终态 succeeded | 健康 |
| 5xx（全部） | 可重试 | 退避后重试 | **不健康** |
| 408 / 423 / 425 / 429 | 可重试 | 退避后重试；429/503 尊重 `Retry-After` | **不健康** |
| 连接失败 / 超时 / 连接重置 | 可重试 | 退避后重试 | **不健康** |
| 其他 4xx（400/401/403/404/409/422…） | **永久失败** | **立刻进死信** | 健康（对方活着） |
| 3xx | 永久失败 | 立刻进死信 | 健康 |
| 模板渲染失败 / payload 非法 / endpoint 未配置 | 永久失败 | 立刻进死信 | 忽略（请求没发出） |
| 本进程优雅关闭导致的取消 | 可重试 | 重新排期 | **忽略**（不是下游的错） |

两个我认为最值得说明的判断：

**① 4xx 立刻进死信，不消耗重试预算。**
`401` 重试十次也不会突然有权限，`404` 重试十次地址也不会突然存在，`400` 重试十次格式也不会突然对。
把它们和 5xx 一样重试 8 次，唯一的效果是把"需要人介入"这个事实推迟几十分钟才暴露。
`TestPermanentFailureGoesToDeadLetterImmediately` 断言了这条通知只尝试 1 次就进死信。

**② 4xx 不触发熔断。**
熔断器度量的是「下游是否可用」，而 4xx 恰恰证明下游是活着的——它能连接、能解析、能回响应。
如果用业务失败去触发熔断，某个业务方推了一批脏数据（大量 400）就能熔断掉整条通道，
连带把其他业务方的正常通知全部堵住。
代码里我把这个区分显式命名为 `Verdict`（健康/不健康/忽略），和业务层的 `Outcome` 分开，
`TestBusinessFailuresDoNotTripTheBreaker` 锁住了这个行为。

### 4.3 退避策略

`delay = min(base × 2^(attempt-1), max)`，再叠加 ±jitter 比例的对称抖动。

**抖动不是可选项。** 没有它，一次下游全站故障会让成千上万条通知在同一毫秒集体到期重试，
把刚刚恢复的下游第二次打挂（惊群）。代价只是重试时刻不再精确可预测，这个代价可以接受。

**`Retry-After` 优先于自己的退避曲线**，但夹在 `backoff.max` 以内——
下游比我们更清楚自己什么时候能恢复，但一个配错的 `Retry-After: 86400` 不能把通知冻住一整天。

### 4.4 外部系统长期不可用时的完整策略

这是需求明确问到的场景。我的处理是一条有明确终点的链路，而不是无限重试：

```
下游开始返回 5xx
   │
   ├─ 第 1..N 次失败：指数退避重试（1s, 2s, 4s, 8s...，带抖动）
   │
   ├─ 连续失败达到阈值 → 熔断打开
   │     ├─ 停止领取该 endpoint 的任务（不再对下游施压）
   │     ├─ attempt 不再增加（不消耗重试预算）← 关键
   │     ├─ 其他 endpoint 完全不受影响
   │     └─ 指标 notify_breaker_state / notify_breaker_trips_total 变化，可告警
   │
   ├─ 冷却结束 → 半开，放 1 个探测请求
   │     ├─ 探测成功 → 熔断关闭，积压通知按退避曲线陆续送达
   │     └─ 探测失败 → 重新熔断并再冷却一轮
   │
   └─ 若下游一直不恢复，通知最终耗尽重试预算 → 进死信
         ├─ 日志用 WARN 级别输出（可直接对应告警规则）
         ├─ 指标 notify_terminal_total{state="dead"} 增长
         ├─ 运维通过 GET /v1/notifications?status=dead 巡检
         └─ 下游修好后 POST /v1/notifications/{id}/retry 重投
               └─ 追加预算而不清零 attempt，保留"被人工救过"的历史
```

**为什么最终要进死信而不是永远重试：** 无限重试会让队列无界增长，
并且掩盖了一个事实——这个供应商已经坏了很久，需要人去看。死信是一个**主动制造的可见性事件**。

**优雅关闭**：收到 SIGTERM 后，先关 HTTP 入口（不再接新任务），
再给在途投递一段 grace 时间跑完；超时未完成的会被取消，
worker 把失败结果正常写回并重新排期（而不是硬掐导致状态不明）。
`TestGracefulShutdownLosesNothing` 验证了关停 + 重启后 12 条通知一条不少全部送达。

### 4.5 一个刻意做出的取舍：崩溃也消耗重试预算

lease 过期被回收时，`attempt` 会 +1。

这看起来"不公平"（这次失败不是通知本身的问题），但如果不这样做，
一条能稳定打挂进程的"毒任务"会被无限次回收重放，
把单条脏数据放大成全系统不可用。预算耗尽后它会进死信等人工处理，
这是把故障限制在一条记录内的代价。`TestRecoverExpiredLeasesMovesExhaustedTaskToDead` 锁住了这个行为。

## 五、关键工程决策与取舍

### 5.1 用数据库当队列，不引入消息队列

这是全局最大的一个决策，需求里也明确要求说明中间件选择。

**为什么选 SQLite（嵌入式数据库当队列）：**

- 通知投递需要的队列语义很特殊：**延迟重试**（第 3 次失败后 4 秒再来）、
  **按 key 幂等**、**单条任务状态可查询**、**死信可人工重投**。
  这四件事用 SQL 表天然就有（`next_attempt_at` 字段 + 唯一索引 + 主键查询 + UPDATE），
  而用 Kafka 实现每一件都要额外机制（延迟队列/死信 topic/外挂 KV 做状态查询）。
- 通知系统的核心价值是**状态可查、可人工干预**。运维一定会问"我那条通知怎么了"，
  这需要随机读单条记录——这正是数据库擅长、消息队列不擅长的。
- 第一版的量级（企业内部事件通知，量级通常是每天几万到几百万）
  离 SQLite 的写吞吐上限还很远，而它带来的运维成本是**零**。
- 零依赖对这个作业还有一个具体好处：`git clone && make demo` 就能跑通完整的故障演练，
  评审不需要装 Docker。

**为什么不用 Kafka / RabbitMQ / RocketMQ：**

引入 MQ 会立刻带来：一套需要运维的集群、消费位点管理、
延迟重试要自己用延迟 topic 或时间轮实现、死信 topic、
以及"消息在 MQ 里但状态在 DB 里"的双写一致性问题。
对第一版来说这些复杂度换不到对应的价值——当前瓶颈不是吞吐。

**为什么不用 Redis：**

Redis 做队列需要自己处理持久化可靠性（AOF everysec 仍可能丢数据）。
本系统的第一条承诺就是"返回 202 就不会丢"，把它建立在一个默认配置会丢数据的组件上不合适。

**不使用 SQLite 时的替代方案（已为此做好准备）：**

换成 **PostgreSQL** 即可，表结构一行不改。`Store` 接口（`internal/store/store.go`）
已经把契约划出来了，`dispatcher` 和 `api` 层零改动。
领取任务的两步事务可以直接换成 `SELECT ... FOR UPDATE SKIP LOCKED`，
甚至比现在更高效。lease 机制本身就是为多实例设计的，天然支持水平扩展。

> 这里有个细节值得说明：我定义 `Store` 接口**不是**为了"可插拔"这种虚的好处
> （现实中几乎没人真的会在运行时换存储），而是因为第一版明确知道会演进到 PostgreSQL，
> 接口划在这里是为了让那次迁移不波及上层。为一个不会发生的扩展点做抽象是过度设计，
> 为一个已经能看到的迁移做抽象是合理准备。

### 5.2 连接池限制为 1 条连接

SQLite 同一时刻只允许一个写者。用 `database/sql` 的多连接去抢写锁，
换来的只是 `SQLITE_BUSY` 和难以复现的抖动。

我把 `MaxOpenConns` 设为 1，让所有写串行化。代价是写吞吐上限，
收益是**零 "database is locked" 错误和完全可预测的行为**。
本服务的事务全是毫秒级短事务，所以这个代价很小。
这也正是演进到 PostgreSQL 的触发条件——当单连接写入成为瓶颈时。

### 5.3 endpoint 注册制：调用方不能传 URL

业务系统提交通知时只给一个逻辑名（`"endpoint": "crm"`），
真实 URL、凭据、超时、重试策略全部由服务配置定义。

三个理由：

1. **防 SSRF**。允许调用方指定任意 URL，就等于在内网里开了一个探测代理。
2. **凭据集中**。供应商 token 不再散落到每个业务系统的配置里。
   配置用 `${env:VAR}` 注入，任何读接口只回显 header 名不回显值
   （`TestEndpointsNeverLeakCredentialValues` 锁住了这一点）。
3. **变更收敛**。供应商换域名或换认证方式时只改这里，所有业务方不需要发版。

代价是接入新供应商需要改配置并重启。我认为这个代价可以接受：
接入频率（几个月一次）远低于通知量（每天几万条），
而且引用了不存在的环境变量会让进程**启动失败**，而不是带着空 token 上线后对每条通知返回 401。

### 5.4 手写 Prometheus 指标，不引入 client_golang

本系统需要的全部指标是 5 个计数器、1 个直方图、3 个 gauge。
手写实现约 200 行且零依赖；`client_golang` 会带进十几个传递依赖，
它们会出现在每一次安全扫描和版本升级里。

这个取舍有**明确的失效条件**：一旦需要 exemplar、原生直方图或 pushgateway，
就应该换成官方库，而不是继续给自己的实现加功能。
写明失效条件，是为了让后来的人知道什么时候该推翻这个决定。

### 5.5 指标标签必须用固定值域

`notify_ingress_total{endpoint="..."}` 的 endpoint 来自请求体。
未注册的 endpoint 统一归到 `_unknown`，绝不把调用方传来的任意字符串当标签值。

这是 Prometheus 标签基数爆炸最经典的事故成因：一次拼写错误的循环调用
就能生成上万条时间序列，把监控系统打挂。
`TestMetricsExposesIngressCounters` 显式断言了这个行为。

### 5.6 时间有序 ID（ULID 布局），不用 UUIDv4 也不用自增

26 字符 Crockford Base32，48 位毫秒时间戳 + 80 位随机。

- 不用 UUIDv4：随机主键让每次插入落在 B-tree 的随机位置，造成页分裂和缓存失效。
- 不用自增：多实例写同一张表需要中心化协调，而且自增 ID 会泄露业务量级。
- 用 Crockford 字母表（去掉 I/L/O/U）：这个 ID 是要被人复制粘贴到工单和日志里的，
  避免 0/O、1/I 看错。

### 5.7 其他几个小而具体的决策

| 决策 | 理由 |
|---|---|
| `MaxIdleConnsPerHost = 64` | Go 默认值是 2，对持续向少量固定域名发请求的服务太小，会导致连接反复重建、TIME_WAIT 堆积 |
| 响应体读到 EOF 再关闭 | 不读完连接无法复用，高频投递会退化成每次都新建 TCP+TLS |
| 超时用 per-request context，不用 `client.Timeout` | 一个全局超时无法同时适配"快返回的广告系统"和"慢的 CRM" |
| 模板在启动时编译 | 让语法错误在进程启动时暴露，而不是在凌晨三点的第一条通知上暴露 |
| 入口和调度器共享进程 | 第一版没必要拆成两个服务；`Store` 接口已让未来拆分成本可控 |
| `DisallowUnknownFields` + `KnownFields(true)` | 配置或请求里字段拼错必须报错。静默忽略会让"我明明配了重试次数"变成一场漫长排查 |
| 启动时扫描孤儿 endpoint | 配置里删掉 endpoint 后，存量任务会永远停在 pending。这种"看起来正常、实际永不推进"的状态比报错危险，所以启动时主动告警 |
| `/healthz` 与 `/readyz` 分开 | healthz 答"进程活着吗"（挂了重启），readyz 答"能接流量吗"（DB 挂了摘流而不是重启进程）。`TestHealthAndReady` 断言了这个区别 |
| 只允许取消 `pending` | `in_flight` 的请求可能已落到下游，这时返回"已取消"是给业务方一个我们兜不住的承诺 |

## 六、取舍与演进

### 6.1 AI 方案里我认为"过度"并选择不采纳的设计

完整的 AI 使用记录见 [AI_USAGE.md](./AI_USAGE.md)，这里列出最典型的几条及判断依据。

我的判断标准始终是同一个问题：**这个设计解决的是我现在真实面对的问题，
还是一个我想象出来的未来问题？** 如果是后者，它现在就是纯成本。

| AI 建议的设计 | 不采纳的理由 |
|---|---|
| **Kafka + 独立 Scheduler + Redis 三件套** | 引入三个需要运维的组件来解决一个第一版还不存在的吞吐问题。延迟重试、单条状态查询、人工重投这几个真实需求，用 MQ 实现反而更复杂 |
| **Exactly-once（2PC / 事务消息）** | 承诺做不到的事。下游不配合幂等时，任何协议都无法保证恰好一次。诚实地给 at-least-once + 帮下游去重，比一个有漏洞的 exactly-once 更可靠 |
| **Outbox 模式 + CDC（Debezium）** | Outbox 解决的是"业务数据库事务和消息投递的原子性"，那是**业务系统侧**的问题。本系统是接收方，它的入口就是一次 HTTP 调用，天然没有跨库双写 |
| **JSONata / Jolt 转换 DSL** | 把业务语义搬进通知服务。会让通知服务的发布风险覆盖所有业务方，且 DSL 的调试体验远差于业务代码。只保留一个 30 行的 `text/template` 逃生舱 |
| **每个 endpoint 一个独立 K8s Deployment** | 故障隔离用进程内的独立并发池 + 独立熔断器已经达到，代价是几行代码；拆成 N 个部署的代价是 N 倍的运维和发布负担 |
| **gRPC + Protobuf 双协议入口** | 调用方是内部业务系统，HTTP+JSON 的接入成本最低（curl 就能测）。序列化性能不是瓶颈——瓶颈在外部 API 的网络往返 |
| **OpenTelemetry 全链路 + Jaeger** | 本系统的链路只有两跳（入口→投递）。我用 `X-Notification-Id` 贯穿 + 完整的 attempt 审计记录，已经能回答所有排障问题。真接入 OTel 应该和公司统一方案一起做 |
| **Event Sourcing / CQRS** | 状态机只有 5 个状态、一张表就能表达。事件溯源会把"查一条通知现在什么状态"从一次主键查询变成一次事件重放 |
| **Redis 共享熔断器状态** | 引入一个新的可用性依赖（Redis 挂了熔断器怎么办）来换取多实例熔断状态一致。实际上每个实例独立熔断是可接受的——最坏情况是熔断生效慢一点，而不是错 |
| **管理后台 Web UI** | 死信巡检和重投用 curl + 几个 JSON 接口就能完成。UI 是真实痛点出现后再做的事，不是 MVP |
| **优先级队列 / 多级队列** | 需求里没有任何优先级概念。加了之后要回答"优先级饥饿怎么办"，凭空增加一类问题 |
| **自动死信重投（定时扫描）** | 这个我想得最久，最后决定不做。通知会进死信，说明**自动重试已经失败过了**。再加一层自动重试只是把同样的失败推迟发生，同时掩盖了"有东西坏了需要人看"这个信号。死信应该是一个刺眼的告警，不是一个会自己消失的状态 |
| **动态配置热加载（watch 文件 / 配置中心）** | 第一版接入频率低，重启代价小（优雅关闭不丢消息，已有测试覆盖）。热加载要处理"配置变更时在途任务用新配置还是旧配置"，是真实的复杂度 |

### 6.2 如果流量或复杂度显著增长，我会怎么演进

我把演进拆成有**明确触发条件**的阶段，而不是一份"未来要做的功能清单"——
没有触发条件的演进计划，本质上还是在猜。

**阶段一：单机吞吐到顶（触发条件：SQLite 写入延迟 p99 上升，或队列深度持续增长）**

1. 存储换 PostgreSQL。表结构不变，领取改用 `SELECT ... FOR UPDATE SKIP LOCKED`。
   `Store` 接口已就位，上层零改动。
2. 水平扩容到多实例。**现在就已经支持**：lease 机制天然互斥，
   `instance_id` 用 hostname+pid 区分同机多进程。
3. 把 `synchronous` 从 FULL 降到 NORMAL（如果能接受极端掉电丢最后几毫秒的提交）。

**阶段二：数据量到顶（触发条件：单表超过千万行，或 admin 查询变慢）**

1. 按 `created_at` 做分区表，冷数据归档到对象存储。
   此时已有真实增长曲线，归档策略不再是猜测。
2. `succeeded` 记录缩短保留期（它的审计价值随时间快速衰减），
   `dead` 记录长期保留（它是待处理事项）。

**阶段三：调度成为瓶颈（触发条件：投递延迟被"轮询到期任务"主导，而非外部 API 延迟）**

1. 引入消息队列做「就绪任务」的分发，但**数据库仍是状态的唯一真相**——
   MQ 只做 wake-up 信号，不承载状态。这样能拿到低延迟分发，
   又不引入"消息在 MQ、状态在 DB"的双写一致性问题。
2. 到期重试用时间轮或延迟队列替代轮询。

**阶段四：供应商数量与治理复杂度增长（触发条件：endpoint 超过几十个，或接入频率变高）**

1. endpoint 配置从 YAML 迁到配置中心/数据库，支持动态注册，
   免掉"接入新供应商要改配置发版"。
2. 加全局 QPS 配额（此时才值得引入分布式限流）。
3. 按 endpoint 分组部署，做物理级隔离（把最不稳定的几家单独隔开）。
4. 死信巡检 Web UI、批量重投。

**阶段五：出现新的语义需求**

- 需要顺序保证 → 引入按 key 分区串行化，并明确接受"分区内一条卡住会阻塞后续"这个代价。
- 需要 fan-out → 这时应该讨论的是"是不是该上事件总线"，而不是给通知服务加订阅功能。

**我不会做的演进**：把这个服务做成通用的"集成平台"。
它的价值来自边界清晰——只负责可靠投递。一旦开始承担编排、转换、聚合，
它会退化成一个谁都不敢动的中心节点。

## 七、接口说明

### 业务入口

**`POST /v1/notifications`** — 提交通知

```jsonc
{
  "endpoint": "crm",                  // 必填，配置中注册的逻辑名（不是 URL）
  "idempotency_key": "order-1001",    // 可选，也可用 Idempotency-Key 请求头
  "payload": { "any": "json" },       // 投递内容，默认原样透传
  "headers": { "X-Request-Id": "r1" },// 可选，受放行策略限制
  "max_attempts": 12                  // 可选，覆盖 endpoint 默认重试预算
}
```

| 响应 | 含义 |
|---|---|
| `202` | 新任务已持久化，本服务负责送达 |
| `200` + `duplicate: true` | 幂等键命中已有通知，没有新建任务 |
| `400` | 请求非法（未注册的 endpoint、字段拼错、header 含 CRLF…） |
| `413` | 超过 `max_body_bytes` |
| `503` | 落库失败，请重试（**不会**返回 202） |

### 管理接口（受 `admin_token` 保护）

| 接口 | 用途 |
|---|---|
| `GET /v1/notifications/{id}` | 查询单条通知 + **完整投递尝试历史**（排障主入口） |
| `GET /v1/notifications?status=dead&endpoint=crm&limit=50&before=<RFC3339>` | 列表 / 死信巡检，游标翻页 |
| `POST /v1/notifications/{id}/retry` | 死信重投，body 可带 `{"extra_attempts":3}` |
| `POST /v1/notifications/{id}/cancel` | 取消未投递的通知（仅 `pending`） |
| `GET /v1/endpoints` | 已注册 endpoint + **熔断器实时状态**（不回显凭据值） |

### 运维接口

`GET /healthz`（进程存活）、`GET /readyz`（依赖就绪）、`GET /metrics`（Prometheus）

### 投递给下游时注入的请求头

| Header | 用途 |
|---|---|
| `X-Notification-Id` | 稳定的通知 ID，跨所有重试不变 — **下游用它去重** |
| `X-Notification-Attempt` | 第几次尝试，从 1 开始 |
| `X-Notification-Endpoint` | 逻辑 endpoint 名 |
| `X-Notification-Timestamp` | 通知创建时间（毫秒） |
| `X-Idempotency-Key` | 业务方提供的幂等键（若有） |

### 关键指标

```
notify_ingress_total{endpoint,result}              入口收单（accepted/duplicate/rejected/error）
notify_delivery_attempts_total{endpoint,outcome}   投递尝试（success/retryable/permanent）
notify_terminal_total{endpoint,state}              进入终态（succeeded/dead）
notify_delivery_duration_seconds{endpoint}         投递耗时分布
notify_queue_depth{status}                         队列深度（各状态计数）
notify_in_flight{endpoint}                         当前在途请求数
notify_breaker_state{endpoint,state}               熔断器状态
notify_breaker_trips_total{endpoint}               熔断打开次数
notify_lease_recovered_total                       lease 回收数（持续非零说明有实例异常退出）
```

建议的告警：`notify_terminal_total{state="dead"}` 增长、
`notify_queue_depth{status="pending"}` 持续上升、`notify_breaker_state{state="open"}` 为 1、
`notify_lease_recovered_total` 持续增长。

## 八、测试

```bash
make test        # 111 个用例，约 20 秒
make test-race   # 竞态检测，全部通过
make cover       # internal/ 语句覆盖率 88.1%
```

测试是按「验证承诺」而不是「覆盖函数」来组织的。
最有价值的是 `internal/e2e` 下的 16 个端到端用例——
它们跑的是真实的 HTTP 入口 + 真实的 SQLite 队列 + 真实的调度器 + 真实的 HTTP 投递，
只有外部供应商是可控的假实现：

| 用例 | 验证的承诺 |
|---|---|
| `TestRetriesUntilVendorRecovers` | 下游故障后恢复，通知自动送达，业务方无感 |
| `TestRetryIntervalsGrowExponentially` | 退避真的在退避（断言实际请求时间间隔递增） |
| `TestPermanentFailureGoesToDeadLetterImmediately` | 4xx 只尝试 1 次就进死信，不烧预算 |
| `TestExhaustedBudgetThenManualRequeueSucceeds` | 预算耗尽 → 死信 → 人工重投 → 送达，且历史保留 |
| `TestHonorsRetryAfterOnRateLimit` | 被限流时听下游的 `Retry-After`，而不是自己的曲线 |
| `TestQueueSurvivesRestart` | 队列跨进程重启存活 |
| `TestGracefulShutdownLosesNothing` | 关停 + 重启后 12 条通知一条不少 |
| `TestSlowVendorDoesNotBlockOtherEndpoints` | **故障隔离**：卡死的供应商不拖累健康的 |
| `TestPerEndpointConcurrencyLimitIsEnforced` | 并发上限真的生效（观测下游看到的并发峰值） |
| `TestCircuitBreakerStopsHammeringAndPreservesRetryBudget` | 熔断停止施压，**且不消耗重试预算** |
| `TestBusinessFailuresDoNotTripTheBreaker` | 4xx 不触发熔断，一个业务方的脏数据不影响他人 |
| `TestDuplicateSubmissionDeliversOnlyOnce` | 入口幂等：重复提交 5 次只投递 1 次 |

## 十、已知限制

我认为诚实列出限制比假装完备更有价值：

1. **单机写吞吐上限**（SQLite 单连接串行写）。触发后按 6.2 阶段一迁 PostgreSQL。
2. **多实例下熔断器状态不共享**。每实例独立熔断，最坏情况是整体熔断生效变慢。
3. **数据无归档**，表会持续增长。刻意留到有真实数据后再定策略。
4. **不保证投递顺序**，见 3.2②。
5. **配置变更需重启**，重启不丢消息但会有秒级投递延迟抖动。
6. **业务入口无鉴权**，依赖服务网格 / 网关，见 3.2⑤。
7. **`Retry-After` 被 `backoff.max` 夹住**，下游要求的超长等待不会被完全尊重（有意为之）。
